## 1. Implementation Progress
- File open dialog uses `FileNameExtensionFilter`: Video, Audio, and Picture, then one short filter per format such as `MP4 (*.mp4)`. Long mime groups are split so a label stays within 40 characters.
- SpotBugs `verify` findings are fixed in code. `spotbugs-exclude.xml` keeps only shared collaborators, Swing editors, and live capture objects.
- Chrome/Chromium link drops on Linux: the content window's `XdndProxy` points at the shell, which already has `XdndAware`. The drop reads `text/uri-list`, `text/x-moz-url`, `text/html`, and `text/plain;charset=utf-8`. `text/uri-list` alone is a file list in the JDK, so http(s) links were discarded.
- Player panel reloads title, duration, and streams when the Kodi item identity (file, label, type) changes, including a new link dropped onto an already playing item. Follow-up reads run at 400 ms and 1200 ms after open.
- HTTP byte-range serving for `/vfile` and `/res` now follows RFC 9110 positioning: open ranges, suffix ranges, end past EOF clamped, unsatisfiable ranges return 416 with `Content-Range: bytes */size`.
- Playback reads start at the requested offset through `FileChannel` (or the in-memory payload), and `Content-Length` is the selected slice, including HEAD and clipboard/in-memory payloads.
- A finished range response closes the body stream so the JDK server accepts the next request on that keep-alive connection. A short or aborted body is failed immediately; Kodi otherwise waits about 10 seconds and then stops playback.
- An expired file id is parked for restore for 30 minutes, at most 32 records. A second restore of the same id returns the record that is already registered. Opening a file registers that id once; a failed open removes it. `restartServer` clears both the live map and the parked map.
- Covered by `HttpRangeTest` and `InternalServerRangeTest` (including a second range on the same connection).
- Kodi JSON replies are built through constructors. Jackson no longer writes `final` fields, so the JDK warning about `ActivePlayerInfo.playerid` is gone.

## 2. Architecture & Technical Discoveries
- Linux X11: Chromium's `FindWindowFor` checks `XdndAware` only on the window under the pointer and does not walk parents. Swing draws into a child named "Content window" that has no `XdndAware`, so Chromium never sends `XdndEnter`. `XdndProxy` on that child and on the shell (both set to the shell, type `WINDOW`) makes Chromium deliver the drag to the shell Java already registered. Firefox already walks up to that shell.
- Chrome can send `XdndPosition` with action 0. Java then answers `XdndStatus` with accept 0 unless `dragEnter`/`dragOver` calls `acceptDrag(ACTION_COPY)`.
- JDK flavormap maps `text/uri-list` only to `javaFileListFlavor`. Non-file URIs are dropped, so a Chrome http link arrives as an empty file list. Read `text/uri-list`, `text/html`, and `text/x-moz-url` (UTF-16) as bytes. A native Wayland Chromium talking to an X11 JVM still will not deliver a drop. The running copy in `~/Programs/ravikoodi` is a packaged jar; it does not pick up workspace changes until it is rebuilt.
- Kodi keeps the same player id when a new file replaces the current one. The panel must compare `Player.GetItem` file/label/type; a one-shot full refresh can observe the previous item and then never update the title.
- A slower full refresh used to be discarded when a faster progress refresh painted first (`updateStatusCounter`).
- Kodi seeks by sending `Range: bytes=<offset>-` (sometimes a closed or overshot end) to the embedded `com.sun.net.httpserver` handler in `InternalServer`. After a range is fully read it sends the next one on the same connection. The JDK server reads that request only after the response body is closed. Kodi's file cache waits 10 seconds for the first byte, then the player stops.
- `sendResponseHeaders(status, length)` overwrites `Content-Length` on GET. HEAD does not: the header must be set to the selected length and the length argument must be `-1`. Passing `0` selects chunked encoding. The screencast GET uses `0` and closes the body when the cast ends.
- In-memory payloads (`UploadFileRecord.predefinedData`, used for the clipboard screenshot) are the body. `File.length()` on the placeholder path is not the size.
- `Accept-Ranges: bytes` is what tells the player that seeking is allowed. Screencast stays `Accept-Ranges: none`.
- jsonrpc4j uses one `ObjectMapper`: `ParameterNamesModule` plus `ConstructorDetector.USE_PROPERTIES_BASED`. The compiler writes parameter names (`-parameters`). Lombok copies `@JsonProperty` onto generated constructors. Jackson 2.21 does not apply `@JsonProperty(defaultValue)` when a creator argument is absent, so `ListLimitsReturned` takes `Long` for `start` and `end` and uses 0 and -1 when those keys are missing.
- `java-youtube-downloader` 4.0 replaces request/callback types with `YoutubeDownloader.builder()`, `videoInfoAsync`, and `playlist`. Formats are `muxed`, `videoOnly`, and `audioOnly`. There is no per-request client. The downloader tries its default profiles (visionOS, then Android VR). Samsung TV needs a JS challenge solver and is not used. Playlist videos load lazily and no longer expose `isPlayable`; direct playlist open takes the first listed video. `Empty` is a parameterless JSON-RPC body. Spring Boot 4.2 deprecates `jackson2.JsonComponent` for removal, and that annotation is not used.
- YouTube sign-in follows the Kodi plugin device-code flow: `accounts.google.com/o/oauth2/device/code` with the YouTube TV client, then the user enters the code at google.com/device. The grant is AES-GCM encrypted and stored in the same Java preferences node as the other settings (`youtube.session`, `youtube.session.key`). The Youtube settings tab shows Set or Not set. The button is Set when no token is saved and starts device sign-in; Remove clears the grant immediately. The bearer token is added only to innertube calls whose `X-YouTube-Client-Name` is `7` (TVHTML5). A bot check or HTTP 401/403 opens the sign-in dialog and retries once.
- `spring-boot-maven-plugin` `finalName` is read-only and ignored. The `publishsh` profile sets Maven `build/finalName` to `artifact-version.sh`, then renames that jar to drop `.jar`.

## 3. Technical Debt & Refactoring
- `.webm` is mapped to `video/x-ms-wmv` in `MimeTypes`.
- File-handler path parsing is still string-split on the raw request URI.
- NetBeans `.form` files and `GEN` / `NOI18N` markers are gone. Swing layout lives in the Java sources.
- Nullness annotations are `org.jspecify.annotations.NonNull` and `Nullable`. Spring's `org.springframework.lang` copies are deprecated. `jspecify` comes from the Spring Boot BOM.

## 4. Current Work In Progress
- Concurrency review fixes are in the working tree: screencast dispose no longer joins its own thread, buffer waits instead of spinning, the cast response is chunked and closed, parked files expire, timers cannot reschedule after cancel, and Kodi control calls leave the Swing thread.
- Open-file dialog filters come from `MimeTypes.makeOpenFileFilters()`. Broad filters are the single words Video, Audio, Picture. Format filters use the standard `Name (*.ext)` label. Covered by `MimeTypesTest`.
- SpotBugs check is clean after the fixes. `mvn22 -pl ravikoodi-app -am verify`.
- Chromium drops fail on the packaged app because the content window is not an XDnD target. The workspace now publishes `XdndProxy` after the frame is shown. Parser covered by `LinuxBrowserDropSiteTest`. A live Chromium drag still has to be tried on a rebuilt launch.
- Player-panel refresh after a new link is in the working tree. Not committed.
- Byte-range positioning fix is in the working tree and tested. Not committed.
- Seek no longer leaves a finished range connection unable to accept the next request. Not committed.
- Kodi reply types no longer use a forced no-arg constructor. Covered by `KodiJsonBindingTest`. Not committed. The packaged app in `~/Programs/ravikoodi` needs a rebuild.
- Dependency bump to Spring Boot 4.2.0 and java-youtube-downloader 4.0.0 compiles, tests pass, and SpotBugs is clean. YouTube call sites use the 4.0 API. `publishsh` still emits the `.sh` archive. Not committed.
- YouTube device sign-in is in the working tree: Misc → YouTube account, a refused video opens the code dialog, and the Youtube settings tab can set or remove the sign-in. Not committed.

## 5. Known Issues & Limitations
- YouTube sign-in covers one TV client. A ciphered stream that still needs the JS player can come back with no URL and falls through to the unsigned clients. Kodi-plugin mode does not use this sign-in.
- Multipart ranges (`bytes=0-1,2-3`) are ignored and the whole payload is returned. One range is what players send for seek.
- A short read after headers are sent closes the connection so the player does not wait out its read timeout.
